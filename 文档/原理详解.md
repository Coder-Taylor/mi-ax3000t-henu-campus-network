# 原理详解

这份文档解释"为什么这么配"。不讲操作步骤，那些在
[刷机指南.md](刷机指南.md) 和 [日常使用.md](日常使用.md) 里。

---

## 一、为什么必须刷机

小米原厂固件其实也是 OpenWrt 改的，但它锁死了三样东西：

| 能力 | 原厂 | 刷机后 | 为什么项目需要它 |
|---|:---:|:---:|---|
| SSH 登录 | 锁死 | 完全控制 | 要跑守护进程、看日志 |
| WiFi 客户端模式（STA） | 无 | 有 | 路由器必须"作为一台设备"去连校园网 |
| 自定义脚本 | 无 | 有 | 自动认证靠 shell 脚本 |

第二条是关键。原厂固件里网口只有 WAN（插网线）和 LAN（发 WiFi）两种角色，
**没有"用 WiFi 去连别的 WiFi"这个功能**。而宿舍里没有网线，只能靠无线连校园网。

> 技术上这叫"STA 模式"。家用路由器通常做 AP（别人连我），
> STA 是反过来（我去连别人）。一台设备可以同时做两件——它的 5G 射频当 STA 连校园网，
> 同时 2.4G 射频当 AP 给宿舍发 WiFi。

## 二、校园网认证为什么这么麻烦

### Portal 认证的本质

连上 `henu-student` 之后，你拿到了一个 `10.x.x.x` 的内网 IP，但外网还是不通。
这时候你打开任何网页，防火墙会**劫持这个 HTTP 请求**，返回一个 302 跳转到登录页。

你输入学号密码点登录，浏览器发请求给认证服务器，服务器放行你这个 IP 一段时间。

关键点：**放行是按 IP 给的，不是按设备给的**。所以路由器只要让"路由器自己的那个 IP"
通过认证，后面所有挂在它下面的设备就都能上网——这就是整个方案成立的基础。

### 三步认证分别是什么

逆向我们实际抓包看，河南大学这套系统（华为 + AAA 平台）走三步：

| 步 | 目标 | 端点 | 作用 |
|---|---|---|---|
| 1 | 验证账号密码 | `172.29.35.27:8088/aaa-auth/api/v1/auth` | 提交校编码 + 学号 + 密码 + 运营商后缀 |
| 2 | 二次校验 | `172.29.35.27:8882/user/check-only` | 查询账号状态（是否欠费、是否已在线） |
| 3 | 门户登录 | `172.29.35.36:6060/quickauth.do` | 真正放行的那个请求，要带 WAN IP、时间戳、UUID |

**只有第三步是决定性的。** 前两步是"检查"，第三步才是"开关"。

这一点在实践中很重要：我们遇到过第 8088 接口连不上、但第三步照样认证成功的情况。
所以脚本里前两步失败**不阻断**流程，只记日志。

### check-only 的坑

第二步 `check-only` 的校验非常宽松，账号拼错一点它也可能返回成功。
所以**不能用第二步的成功来判断认证成功**——必须看第三步的返回。

第三步返回的 JSON 里出现 `"message":"认证成功"` 才算通过。

### 运营商后缀

河南大学三家运营商共用一套认证，靠后缀区分：

- `@henuyd` 移动
- `@henult` 联通
- `@henudx` 电信

实测只有 `@henuyd` 稳定。学校里大部分学生用的是移动账号。

### 校编码

`07cdfd23373b17c6b337251c22b7ea57` 是一串 MD5。

它标识"哪个学校的认证系统"，河南大学所有学生填的完全一样。
不是学号、不是身份证、不含任何个人信息，可以随便给别人。

服务器拿到它，就知道"这是河南大学的请求，去河南大学的账号库里查"。

## 三、为什么要两个"自动重连"机制

校园网认证是**有有效期的**。过期之后：

- ICMP（ping）**照常放行**，所以 ping 得通
- HTTP 被劫持到登录页，所以网页打不开

这个组合非常具有欺骗性。如果只看 ping，会以为网络好好的。

### 两个机制的分工

| 机制 | 检查什么 | 间隔 | 擅长处理 |
|---|---|---|---|
| `fast_recovery_daemon.sh` | 路由 + 链路 + HTTP 劫持 | 每秒 / 60 秒 | 物理层、链路层故障，秒级恢复 |
| `auto_login.sh`（cron 调用） | 认证状态 | 5 分钟 | 认证过期兜底 |

守护进程负责"快"，cron 负责"稳"。

### 守护进程的分级处理

它每秒检查一次，命中不同故障用不同手段，越往下越重：

```
Level 1  路由在、STA 连着、没被劫持  → 什么都不做
Level 2  STA 连着但没路由            → 续租 DHCP
Level 3  持续 15 秒没恢复             → 先 DHCP 续租（温和）
Level 4  路由没了、STA 掉了           → 重启 wwan 接口
Level 5  连续失败                     → HTTP 检测 + 重新认证
```

核心思想：**能用轻的手段就不用重的**。DHCP 续租 2 秒就好，重启接口要 10 秒，
重启整个路由器要 90 秒。从轻到重试，能早点恢复。

### 认证失败要退避

如果认证一直失败（比如账号被锁、学校服务器故障），每 60 秒重试一次会撞上
学校的限流，可能把你 IP 拉黑更久。

所以现在的最小重试间隔是 **300 秒**，连续失败 3 次后拉长到 **1800 秒**。

## 四、为什么去掉 `wifi reload`

`wifi reload` 是 OpenWrt 的标准命令，作用是"重新读取无线配置并重启无线子系统"。

听起来无害，但实际做的是：**把所有 WiFi 接口（STA 和 AP）全部关掉，再全部重新初始化。**

2026-10-24 我们抓到了一次崩溃：下载跑到 8MB/s 的时候自动恢复脚本执行了
`wifi reload`，然后路由器整机重启。pstore 里留下了内核栈：

```
mtk_stop → mtk_dma_free → mtk_rx_clean → dma_unmap_page_attrs → dcache_inval_poc
Oops: 96000145, level-1 translation fault
```

这是 MT7981 有线网卡驱动（`mtk_eth`）的 bug：**在 DMA 还在传输时拆掉接收队列**，
访问了已经失效的内存地址。

这个 bug 我们改不了（没有内核源码和编译环境），只能绕开：

```bash
# 原来的做法，会触发崩溃
wifi reload

# 现在的做法，只动 wwan 这一个接口
ubus call network.interface.wwan down
sleep 2
ubus call network.interface.wwan up
```

第二种只拆"连校园网"这一条链路，不碰 WiFi 热点、不碰 LAN 口、不碰 DMA 接收队列。

> 手动操作时也要避开 `wifi reload`，尤其在下载或者看视频的时候。

## 五、CAKE 流控在解决什么问题

### 问题：缓冲膨胀

假设你的带宽是 110Mbit。当你下载跑满时，路由器里会排起一个很长的队列。
你看视频要发的小请求，得排在那些大下载包的后面等。

结果就是：**下载速度很快，但点开网页要等好几秒**。

这叫 bufferbloat（缓冲膨胀）。

### CAKE 的做法

CAKE 是 Linux 里一个智能队列算法，干三件事：

1. **把队列切短**：不让包排太长队，超时就丢。TCP 会自动降速重传，比干等更快
2. **按流公平分配**：`triple-isolate` 按"内网 IP + 外网 IP + 端口"三条线分别隔离。
   一个下载不会挤掉一个微信消息
3. **小包优先**：`ack-filter` 压缩 TCP 的确认包，给真正的数据腾出空间

实测数据：满速下载 58-92Mbps 时，ping 平均 25.7ms（空闲 23.1ms），
**只涨了 2.6ms**，0 丢包。这就是 CAKE 起作用的样子。

### 110Mbit 是怎么定的

这个是**实测**出来的，不是猜的。单流下载测到 66Mbit，多流并发时峰值接近 110Mbit。

经验值：填实测峰值的 85-90%。填太高队列不生效（等于没限速），填太低浪费带宽。

### 为什么要两个方向都配

```
下行数据：校园网 → 路由器 → 你的设备
         ↑ 在 phy1-sta0 上用 ingress 把包重定向到 ifb4phy1-sta0 再排队
         ↑ 因为 Linux 只能对"发出去的包"做流量控制，进来的包要借一个虚拟网卡

上行数据：你的设备 → 路由器 → 校园网
         ↑ 直接对 phy1-sta0 排队就行
```

所以你会看到两个 CAKE 队列：`phy1-sta0`（上行）和 `ifb4phy1-sta0`（下行）。

## 六、DNS 为什么需要四层修复

校园网 DHCP 下发两个 DNS 服务器，两个都有毛病：

- `111.6.174.198`（河南移动）—— 对 `*.henu.edu.cn` 统一返回 `172.31.7.4`（校内门户），
  部分域名返回错误 IP 或空结果
- `114.114.114.114`（公共）—— 对校内域名返回公网 IP，访问不了内网系统

四层修复是**层层兜底**：

### 第 1 层：hosts 写死

```
202.196.96.29   zwyy.henu.edu.cn
58.212.123.41   software.henu.edu.cn
172.31.7.4      net.henu.edu.cn
```

最可靠——不再查 DNS，直接用。缺点是域名换 IP 就失效，需要手动改。

### 第 2 层：UCI 精确域名转发

让 dnsmasq 对特定域名用指定的上游 DNS：

```
xg.henu.edu.cn    →  114.114.114.114
jwgl.henu.edu.cn  →  111.6.174.198
```

针对"某个域名只有某个 DNS 认识"的情况。

### 第 3 层：rebind 豁免

dnsmasq 有个安全机制：如果域名解析结果返回私有 IP（`192.168.x.x`、`172.16-31.x.x`、
`10.x.x.x`），会怀疑这是 DNS rebind 攻击，**丢弃这个结果**。

但校园网正好是全校用私有 IP。所以必须豁免：

```
rebind-domain-ok=/henu.edu.cn/
rebind-domain-ok=/ntp.org.cn/
```

**这里踩过一个坑**：原来把这两行写在 `/etc/dnsmasq.conf` 里，
但 OpenWrt 的 dnsmasq 运行配置是从 uci 生成的，会覆盖掉手改的内容。
日志每 4 分钟报一次 `possible DNS-rebind attack detected: cn.ntp.org.cn`，
说明豁免根本没生效。正确做法是用 uci 写：

```bash
uci add_list dhcp.@dnsmasq[0].rebind_domain='henu.edu.cn'
uci add_list dhcp.@dnsmasq[0].rebind_domain='ntp.org.cn'
```

### 第 4 层：过滤 IPv6

`filter_aaaa=1`，让 dnsmasq 不返回 AAAA 记录。

原因：这台路由器没有 IPv6 出口（校园网只给 IPv4）。如果客户端拿到 IPv6 地址，
会优先尝试 IPv6 连接，全部超时后才回退到 IPv4——表现就是"每次打开新网站都卡几秒"。

## 七、开机链路为什么容易出错

这台路由器的启动顺序是：内核 → `/etc/init.d/` 下按 `START` 数字从小到大依次启动。

我们的服务需要网络和 WiFi 都就绪，所以排在最后（`START=99`）。

### 踩过的三个坑

**坑 1：busybox crond 不支持 `@reboot`**

标准 Linux 的 crontab 支持 `@reboot`（开机运行一次）、`@daily`（每天）这些简写。
但这台路由器的 busybox 是精简编译的，**没编译这个功能**。

遇到 `@` 开头的行，crond 直接崩溃退出。而 procd 会反复拉起它，进入崩溃循环——
结果是连正常的 `*/5` 兜底认证也一起失效了。

> 正确做法：开机任务交给 `/etc/init.d/` 下的服务脚本，crontab 只写标准时间格式。

**坑 2：自定义 `boot()` 覆盖了默认行为**

OpenWrt 的 `/etc/rc.common` 默认提供 `boot() { start "$@"; }`。
如果你自己写了个 `boot()` 但里面没调 `start`，开机时会什么都不执行。

表现就是：服务在 `enable` 之后状态显示"已启用"，但开机后根本不在跑。
这是 v3 版本的问题——开机认证从来没执行过，全靠守护进程兜底，所以看起来"能用"。

**坑 3：`procd respawn 0` 是"无限重启"不是"不重启"**

procd 是 OpenWrt 的进程管理守护。`respawn threshold` 参数的本意是
"崩溃多少次之后放弃"，但填 `0` 会被理解成"永远不放弃"。

结果 `boot_auth.sh` 每 6 秒被拉起一次，一直重复请求认证服务器。

> 正确做法：一次性任务不要用 procd，直接写普通启动脚本，用 `&` 后台跑。

## 八、DHCP 租约为什么设 168 小时

原来默认是 12 小时。设备离开超过 12 小时回来，租约就过期了，
必须走完整 DHCP 协商：广播 DISCOVER → OFFER → REQUEST → ACK，四次来回。

在宿舍这种密集 WiFi 环境里，一次完整协商会产生大量广播帧，
2.4G 上信号弱的设备可能因为收不到 ACK 被踢下线——一个设备回家，全屋断网。

设成 168 小时（7 天）之后，设备短期离开回来只需走两次（REQUEST → ACK），
广播帧少得多，连锁反应就消失了。

## 九、hostapd 为什么要把手机踢下去

`hostapd` 是 WiFi 热点服务。它有个参数 `ap_max_inactivity`，默认 300 秒。

意思是：如果一个客户端 300 秒没有发任何数据，就认为它已经不在了，主动摘掉它。

配合 `skip_inactivity_poll=1`（不主动发探测帧确认）之后，息屏的手机
5 分钟就会被摘掉。唤醒时要重新关联 + WPA 握手 + 拿 IP，第一批请求就卡住了。

改法：

```bash
uci set wireless.default_radio0.max_inactivity='86400'   # 24 小时
uci set wireless.default_radio1.max_inactivity='86400'
```

代价是：真正离开的设备会占着 ARP 表 24 小时。但这台路由器最多连接十几台设备，
无所谓。

## 十、两个监控工具的区别

| 工具 | 数据来源 | 看什么 |
|---|---|---|
| nlbwmon | 内核 netfilter 计数 | 每台设备、每种协议用了多少流量 |
| collectd | 定期采样 | CPU、内存、负载、WiFi 客户端数、Ping 延迟的长周期曲线 |

注意：**开了硬件流量卸载之后，`ifconfig` 和 `/proc/net/dev` 的计数器不准**。
因为包走了硬件快速路径，绕过了软件计数。

想知道真实流量，用 LuCI 的带宽监控——那个在 NAT 之前统计。

## 十一、这个方案的边界

诚实地讲清楚做不到的事：

**做不到 1：关掉认证还能远程开回来**

认证一关，路由器就没网了。而所有远程手段（VPN、SSH、云端文件）都要走网络。
这是死结，物理上无解，除非给它第二条不受校园网管制的网络（4G 模块之类）。

可行的折中：带定时的关闭（`off 2h`，到点自己恢复），或者只停自动重连但保留当前会话。

**做不到 2：修内核 bug**

`wifi reload` 的崩溃是驱动层的问题，没有源码和编译环境改不了。
只能在使用层面绕开。

**做不到 3：保证不被学校发现**

学校如果查"一个账号多个 MAC 在线"，理论上能查到。这个特殊账号
（学号带 `ls` 后缀）实测允许多设备在线，普通账号不允许。

**做不到 4：无限安装插件**

233MB 内存，系统本身和现有服务已经占了 180MB 左右。
再加带 Web 界面的插件很快就会 OOM。
