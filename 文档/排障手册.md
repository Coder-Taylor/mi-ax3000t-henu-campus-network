# 排障手册

按**症状**查，不按时间顺序查。

每条都是：怎么确认 → 怎么办。命令都在路由器上执行（`ssh root@192.168.1.1`）。

---

## 先学会看这两个地方

90% 的问题，答案在这两个文件里。

### 认证日志

```bash
tail -50 /tmp/campus_network.log
```

看最后 50 行。找关键词：`认证成功`、`认证失败`、`被劫持`、`FastRecovery`。

### 卡顿探针日志

```bash
tail -50 /overlay/probe.log
```

每分钟记录一次视频/图片站点的响应时间。带 `卡顿:` 的行说明那一刻确实慢，
同一行里有当时的 WiFi 信号、CAKE 计数、RTT，能直接看出问题在哪层。

## 症状：网页打不开 / 一直转圈

### 第一步：分清是"没网"还是"被劫持"

```bash
ping -c 3 223.5.5.5
curl -s -o /dev/null -w '%{http_code}\n' --max-time 8 http://www.baidu.com
```

| ping 通 | 百度返回 200 | 结论 |
|:---:|:---:|---|
| 通 | 200 | 网是通的，问题不在路由器 |
| 通 | 302 | **认证过期了**，HTTP 被劫持到登录页 → 见下面"被弹登录页" |
| 不通 | — | 链路问题 → 见下面"完全没网" |

> **为什么不 ping 8.8.8.8**：校园网屏蔽了它和 114.114.114.114 的 ICMP，
> 永远 100% 丢包。拿它判断网络状态会一直误判"网断了"。

### 第二步：如果网是通的，但只有手机卡

看是不是手机被 hostapd 以"空闲"理由踢了：

```bash
logread | grep -i 'due to inactivity' | tail -10
```

如果看到很多 `disassociated due to inactivity`，说明手机息屏几分钟就被摘掉，
唤醒后要重新关联 + 握手，第一批请求就卡在这一两秒。

**修复**（已写入配置，重启后生效）：

```bash
# 两个 AP 接口都要改（先确认配置名：uci show wireless | grep -E "mode='ap'|ssid="）
uci set wireless.default_radio0.max_inactivity='86400'
uci set wireless.wifinet0.max_inactivity='86400'
uci commit wireless
```

> 改完不要用 `wifi reload` 热重启——2026-10-24 实测这个命令在负载下会触发
> 内核 Oops。等下次重启（每周一/周四 4:00 自动重启）生效。

### 第三步：跑一次分层测试

在电脑上跑，不是路由器上：

```bash
curl -s -o /dev/null -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer}\n' https://www.bilibili.com
```

正常值参考（实测）：DNS 20-60ms，TCP 30-100ms，TLS 50-260ms，TTFB 60-520ms。

- DNS 特别大（>500ms）→ DNS 问题，见"校内网站打不开"
- TCP 大但 TLS 正常 → 链路问题
- TLS 大 → 对端的问题或链路抖动
- 全部正常但页面还是转圈 → 大概率是浏览器/App 自己的问题

## 症状：能上网，但网页被弹到校园网登录页

这是**认证会话过期**。校园网只劫持 HTTP，ICMP 照常放行，所以 ping 得通、
但网页会被 302 跳到登录页。

### 立刻修复

```bash
/etc/campus_network/auto_login.sh --force
```

`--force` 跳过网络预检，直接走完整三步认证。

### 确认修好了

```bash
tail -20 /tmp/campus_network.log | grep -E '成功|失败'
```

出现 `认证成功` 或者 `message":"认证成功"` 就是好了。

### 为什么守护进程没自动处理

守护进程每 60 秒做一次 HTTP 劫持检测。正常情况下 1 分钟内会自动重认证。
如果一直不恢复，看：

```bash
ps | grep [f]ast_recovery
grep FastRecovery /tmp/campus_network.log | tail -20
```

进程不在就重启服务：

```bash
/etc/init.d/fast_recovery restart
```

### 如果反复被顶下线

可能是账号在别处登录了。这个特殊号（学号带 `ls` 后缀的）允许多设备同时在线，
普通账号不允许——一边登录另一边会被踢。

## 症状：完全没网（ping 也不通）

按层次往上查，从下往上。

### 第 1 层：WiFi 客户端还连着吗

```bash
iw dev phy1-sta0 link
```

- 显示 `Not connected` → 校园网 AP 掉了 → 跳到第 3 层
- 显示 `Connected to ...` → 继续第 2 层

### 第 2 层：拿到 IP 了吗

```bash
ip -4 addr show dev phy1-sta0 | grep inet
ip route | grep default
```

- 没有 `inet 10.x.x.x` → DHCP 没成功 → 续租
- 有 IP 但没有默认路由 → 路由丢了 → 看守护进程日志

```bash
# 续租
kill -USR1 $(cat /var/run/udhcpc.phy1-sta0.pid 2>/dev/null) 2>/dev/null || ifup wwan
```

### 第 3 层：重连校园网

```bash
ubus call network.interface.wwan down
sleep 2
ubus call network.interface.wwan up
```

等 10 秒，回到第 1 层再查。

> **不要用 `wifi reload`**。这个命令会把所有 WiFi 和 LAN 一起关掉再开，
> 在有大流量传输时会触发 mtk_eth 驱动的空指针崩溃，整个路由器重启（pstore 里有记录）。
> 只重启 wwan 这一个接口就够了。

### 第 4 层：路由器本身正常吗

```bash
uptime
free -m
dmesg | tail -20
ls /sys/fs/pstore/
```

- `uptime` 显示刚启动 → 路由器重启过，说明它自己崩了
- `free -m` 的 available 低于 10MB → 内存耗尽
- `pstore/` 里有 `dmesg-ramoops-*` → 有崩溃现场，`cat` 出来看栈

## 症状：校内网站打不开（教务、图书馆、学工）

校园网下发的 DNS（`111.6.174.198`）对部分 `*.henu.edu.cn` 返回错误或空结果。

### 一键修复

```bash
sh /etc/campus_network/dns_fix.sh
```

### 确认修好了

```bash
nslookup zwyy.henu.edu.cn      # 应该返回 202.196.96.29
nslookup net.henu.edu.cn       # 应该返回 172.31.7.4
```

### 查是哪个环节出问题

```bash
# 1. hosts 有没有写死
grep henu /etc/hosts

# 2. DNS 分流规则在不在
uci show dhcp | grep henu

# 3. rebind 豁免生效了吗
grep rebind /var/etc/dnsmasq.conf.cfg*

# 4. 直接问上游 DNS
nslookup zwyy.henu.edu.cn 114.114.114.114
nslookup zwyy.henu.edu.cn 111.6.174.198
```

第 3 步应该能看到 `rebind-domain-ok=henu.edu.cn` 和 `rebind-domain-ok=ntp.org.cn`
两行。**如果没有**，说明只写在 `/etc/dnsmasq.conf` 里而没通过 uci 配置，
uci 生成的运行配置会把它丢掉：

```bash
uci add_list dhcp.@dnsmasq[0].rebind_domain='henu.edu.cn'
uci add_list dhcp.@dnsmasq[0].rebind_domain='ntp.org.cn'
uci commit dhcp
/etc/init.d/dnsmasq reload
```

## 症状：后台打不开 / SSH 连不上

```bash
ping 192.168.1.1
```

- **通** → 服务挂了，重启对应的：
  ```bash
  /etc/init.d/uhttpd restart    # Web 后台
  /etc/init.d/dropbear restart  # SSH
  ```
- **不通** → 检查电脑 IP 是不是 `192.168.1.x`；换个 LAN 口插网线试试

### SSH 提示 Permission denied

不一定是密码错，可能是密钥没被提供。指定密钥文件：

```bash
ssh -i ~/.ssh/ax3000t_rsa root@192.168.1.1
```

如果有一台以上路由器，先确认连的是哪台（`~/.ssh/config` 里两个别名指向不同 IP）。

## 症状：cron 完全不工作，兜底认证不跑

```bash
ps | grep [c]rond
```

没有输出 = crond 没在跑。看 crontab 里有没有 `@` 开头的行：

```bash
grep -n '^@' /etc/crontabs/root
```

有输出就把那几行删掉。这台路由器的 busybox crond 不支持 `@reboot` / `@daily`，
遇到会直接崩溃退出，procd 反复拉起进入崩溃循环，连 `*/5` 也一起失效。

### 开机认证没执行

```bash
grep BootAuth /tmp/campus_network.log
```

没有 `BootAuth` 记录 = 开机没跑认证。检查启动脚本：

```bash
cat /etc/init.d/campus_auth
```

必须满足两个条件：

1. `START=99`（等其他服务都起来）
2. 里面**没有**自定义的 `boot()` 覆盖 rc.common 的默认行为，或者 `boot()` 里显式调了 `start`

历史教训：v3 版本用了 `procd` + `respawn 0`，procd 把 0 当成"永远重启"，
`boot_auth.sh` 每 6 秒被拉起一次，日志刷屏还反复请求认证服务器。
现在的 v4 是**非 procd 的一次性脚本**，用 `&` 后台跑。

## 症状：大流量下载时路由器重启

先确认是不是真的重启了：

```bash
uptime
ls /sys/fs/pstore/
```

`uptime` 很短 + pstore 里有记录 = 内核崩溃。

```bash
cat /sys/fs/pstore/dmesg-ramoops-0
```

已知的崩溃路径：`mtk_stop → mtk_dma_free → mtk_rx_clean` 空指针。
触发条件是**满流量传输时执行完整的 `wifi reload`**。

**规避方法**（已写入脚本）：

- 恢复脚本里不再用 `wifi reload`，改用 `ubus call network.interface.wwan down/up`
- 手动操作时同样避开 `wifi reload`，尤其在下载中

> pstore 只有 4 块存储位，满了之后 `ls /sys/fs/pstore/` 会显示 `(dmesg-ramoops-N: ENOSPC)`，
> 新的崩溃记录存不进去。清理：
> ```bash
> rm -f /sys/fs/pstore/*
> ```

## 症状：手机连上 WiFi 但显示"无互联网"

先确认是真没网还是误报：

用手机浏览器打开 `http://www.baidu.com`。能开就是误报——手机连的是
"是否有互联网"的探测地址，校园网有时会干扰这个探测。

如果真打不开，按"网页打不开"那一节查。

## 症状：半夜突然断网，早上又好了

看是不是赶上了定时重启：

```bash
cat /etc/crontabs/root | grep reboot
```

现在配的是每周一、周四凌晨 4:00 重启，重启期间断约 90 秒。

如果不想半夜重启：

```bash
vi /etc/crontabs/root        # 改时间或删掉那行
/etc/init.d/cron restart
```

## 症状：内存告急

```bash
free -m
```

233MB 总内存，`available` 长期低于 15MB 就该处理了。

```bash
# 看谁占得多
ps | sort -k 4 -rn | head -10
```

常见的大户：LuCI 的 Web 进程（每个插件一个）、collectd、adblock 的 dnsmasq 规则表。

临时缓解：

```bash
/etc/init.d/uhttpd restart     # 重启 Web 服务，释放 LuCI 进程
```

长期方案是停掉不用的插件：

```bash
/etc/init.d/<服务名> stop
/etc/init.d/<服务名> disable
```

## 症状：WiFi 信号变差了

如果刷机前信号正常、刷机后变差，可能是 Factory 分区（WiFi 校准数据）没保住。

检查备份还在不在：

```bash
# 在电脑上
ls 小米AX3000T刷机教程openwrt大分区版\step1解锁ssh\xmir-patcher-main\backups\mtd4_Factory.bin
```

这个文件每台机器都不一样，丢了只能用同型号别人的，信号会差一些。

## 还是搞不定

按这个顺序收集信息，再找人或找 AI 帮忙：

```bash
# 1. 环境快照
date; uptime; free -m

# 2. 链路状态
iw dev phy1-sta0 link
ip -4 addr show dev phy1-sta0
ip route | grep default
ping -c 3 223.5.5.5

# 3. 认证日志
tail -60 /tmp/campus_network.log

# 4. 系统日志
logread | tail -40

# 5. 崩溃记录
ls /sys/fs/pstore/

# 6. 探针日志
tail -30 /overlay/probe.log
```

把这六段一起贴出来，基本能定位问题。
