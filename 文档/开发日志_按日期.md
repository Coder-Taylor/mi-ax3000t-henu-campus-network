## 2026-06-18（周四）— Phase 13：设备重连断联修复 v3

### 问题
用户发现设备 A 离开半天后重连 WiFi，会导致其他设备断联；短时间离开则不会。

### 排查
| 检查项 | 发现 |
|--------|------|
| DHCP 租约 | `12h` ← 精准匹配"半天"阈值 |
| 2.4G disassoc_low_ack | `1` (开启) ← 5G 是 0 |
| 2.4G skip_inactivity_poll | `0` (轮询) ← 5G 是 1 |
| UAPSD | 两个频段都开启 |
| PMKSA 缓存 | 两个频段都禁用 |

### 修复 (5 项)
1. **2.4G 配置对齐 5G**：`disassoc_low_ack=0`, `skip_inactivity_poll=1`
2. **DHCP 租约 12h → 168h**：消除 12h 硬边界
3. **UAPSD 关闭**：避免省电模式导致的 ACK 延迟
4. **PMKSA 缓存开启**：重连跳过 PBKDF2 推导，快速平稳
5. **wifi reload** 验证：所有配置生效，STA 和 AP 自动恢复

### 根因
DHCP 租约 12h 过期 → 设备重连用 DISCOVER（非 REQUEST）→ 大量广播帧 → `disassoc_low_ack=1` 踢掉弱信号设备 → 连锁断联。

### 命令
```bash
uci set wireless.default_radio0.disassoc_low_ack='0'
uci set wireless.default_radio0.skip_inactivity_poll='1'
uci set wireless.default_radio0.wpa_group_rekey='86400'
uci set wireless.default_radio0.uapsd='0'
uci set wireless.default_radio0.auth_cache='1'
uci set wireless.wifinet0.uapsd='0'
uci set wireless.wifinet0.auth_cache='1'
uci set dhcp.lan.leasetime='168h'
uci commit wireless && uci commit dhcp
wifi reload
```

### 二、河南大学 250 个网站 DNS 全量测试

**数据来源**：`主管主办网站.xlsx`（河南大学信息化管理办公室2025年11月数据），共 259 条网站记录。

**方法**：将 250 个 `*.henu.edu.cn` 子域名在路由器上分别用 111.6.174.198 和 114.114.114.114 做 DNS 解析，对比结果。

**结果**：
| DNS 服务器 | 返回 IP | 覆盖域名数 |
|------------|---------|-----------|
| 111.6.174.198（河南移动）| `172.31.7.4`（校内统一门户）| ~248/250 |
| 114.114.114.114（114DNS）| `58.212.123.41`（校外 IP）| ~220/250 |
| 114.114.114.114 | `211.142.109.84`（非标准）| ~17/250 |

### 五、挖出 bug 2：campus_auth 的开机认证其实从未执行过 🔴

`/etc/init.d/campus_auth` 的 procd 实例状态：

```
"exit_code": 2,
"command": ["/bin/sh", "-c", "\n  # 等待 WiFi STA 就绪...\n  for i in 1\n2\n3\n...\n12; do ..."]
```

**根因有两层**（修掉第一层后开机仍然不执行，才挖出第二层）：

1. 旧版用 `procd_set_param command /bin/sh -c "多行脚本"`，脚本里 `$(seq 1 12)` 在注册时
   被 init 脚本的 shell 展开成**换行分隔**的一串数字，procd 记录的命令执行返回 2（`exit_code: 2`）。
2. **更关键的一层**：`/etc/rc.common` 的默认 `boot()` 是 `boot() { start "$@"; }`，
   而旧脚本自定义了 `boot()`（里面只调 `route_watchdog.sh`），**把默认行为覆盖掉了**。
   开机时 rcS 调用的是 `boot`，于是 procd 实例根本不会注册 —— 认证自然永远不执行。
   （手动 `/etc/init.d/campus_auth start` 是能跑通的，所以这个 bug 藏了很久。）

```
"exit_code": 2,
"command": ["/bin/sh", "-c", "
  # 等待 WiFi STA 就绪...
  for i in 1
2
3
...
12; do ..."]
```

也就是说：**自用机运行几个月，开机认证一直不是 campus_auth 干的**，而是
`fast_recovery_daemon` 每秒检测 + 每 60 秒 HTTP 门户劫持检测兜住的（这也解释了为什么开机恢复要几分钟）。

**修复**（三层都要治）：

```sh
#!/bin/sh /etc/rc.common
# 最终版：非 procd 的一次性脚本（v4）
START=99

start() {
	/etc/campus_network/boot_auth.sh &      # 后台执行；它内部会等网络就绪（最长10分钟）
}

boot() {
	/etc/campus_network/route_watchdog.sh   # 早期加速 STA 重连
	start                                    # 必须调用，否则覆盖了默认 boot(){ start "$@"; }
}
```

**第三层坑**：修好前两层、改用 procd + `respawn 0` 之后，procd 把 `threshold=0`
理解成"**永远重启**"——`boot_auth.sh` 每 6 秒被拉起一次（无限循环：日志刷屏 + 反复请求认证服务器）。
用 `ubus call service list` 看到 `running: true` 但 pid 一直在变才发现。
最终**放弃 procd**，改成上面这种一次性脚本（跑完即退出，没有常驻实例可重启）。

## 2026-10-10（周五）— 待售机"一直弹登录页"排查 + 修掉两个脚本缺陷

### 一、现象

待售机（192.168.1.2）下设备上网一直被弹到校园门户登录页。

### 二、三种拒绝的含义（重要，别再反复重试）

| 第三步返回 | 含义 | 正确应对 |
|---|---|---|
| `帐号已经在线，不允许更多登陆` | 该账号已有在线会话（**含我们自己那条**）。实测这套系统**允许多设备同账号同时在线**（账号主人的电脑与本路由器同时在网），此错误应理解为"拒绝重复登录已有会话" | 别重试；等数据通道恢复 |
| `limit exceed ... Request Deny by ha.chinamobile.com` | 短时间反复尝试触发**运营商侧登录限流** | 停止重试，等自动解除（本次约 10 分钟） |
| `认证失败,原因:`（**原因为空**） | 当前 IP 有残留会话（08-30 记录过） | 当时解法是重启路由器（本次无效，见下） |

### 三、本次根因

- 校园侧的**会话记录一直在**（所以重新登录被拒"已经在线"——拒绝的是"重复登录"，**不是**"第二台设备"；本校园网允许多设备同账号并存），
  但会话的 **HTTP 数据通道被掐了一段时间** → 表现为"设备一直被弹登录页"
- **重启路由器无效**：会话在校园侧，不在路由器上
- 最终是**校园侧自行恢复**（不是脚本、也不是某次手动登录的功劳）

> **更正**：本次排查一开始推断"这套系统不允许多设备共存"，后经实测确认**是允许的**
> （账号主人的电脑和本路由器同时在网）。

> ⚠️ **教训**：遇到"已经在线 / 原因为空"这类错误，**千万别反复重试**——
> 会把账号推到运营商限流，反而拖慢恢复。这正是下面第 3 条要修的。

### 四、修掉的两个脚本缺陷

**1. `check_http_portal` 依赖 `curl`（关键）**

新刷的 ImmortalWrt **不带 curl**，`code=$(curl ...)` 永远为空 →
"会话过期"永远检测不到（日志一路"网络已连通"，用户却一直看到登录页）。

```sh
# 改为 curl 可选：没有 curl 时退回 busybox wget + 门户特征串判断
if command -v curl >/dev/null 2>&1; then
    code=$(curl -s -o /dev/null -w "%{http_code}" --max-time 6 http://www.baidu.com 2>/dev/null)
    [ "$code" = "302" ] && return 0
    return 1
fi
body=$(wget -q -O - -T 6 http://www.baidu.com 2>/dev/null | head -c 3000)
[ -z "$body" ] && return 1
echo "$body" | grep -qE 'usertemp|henu-jinming|wlanacname|wlanuserip' && return 0
```

**2. 特征串误判（自己踩的坑）**

第一版用 `/portal/` 当特征串，结果**真实百度页面**里的工信部备案链接
`//www.beian.gov.cn/portal/registerSystemInfo` 就命中 →
守护进程会把**正常状态误判成"被劫持"**，每 5 分钟无谓重认证（又会触发运营商限流）。
→ 改严为校园门户皮肤特有的 `usertemp|henu-jinming|wlanacname|wlanuserip`
（实测真实百度页命中数 = 0）。

> **教训**：拿来做"异常特征"的字符串必须**专属且稳定**，别用 `/portal/` 这种通用词。

**3. 认证重试退避**

原来检测到劫持后每 60 秒重试一次 → 撞上运营商限流。
→ 改为最小间隔 **300 秒**；连续失败 3 次后改为 **1800 秒**。

### 五、顺带
